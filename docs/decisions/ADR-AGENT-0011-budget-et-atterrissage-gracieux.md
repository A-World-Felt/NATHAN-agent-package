# ADR-AGENT-0011: Budget and graceful landing rather than a hard cutoff

- **Status**: ✅ Accepted
- **Date**: 2026-07-21
- **Deciders**: Arthur-Olivier Fortin
- **Scope**: `@a-world-felt/nathan-agent-core`
- **Complements**: [ADR-AGENT-0003](ADR-AGENT-0003-terminaison-boucle-machine-etats.md), whose termination decision (absence of a tool call) stays unchanged. Only the **bounding** mechanism changes.

## Context

`ADR-AGENT-0003` established natural termination: empty `toolCalls` ⇒ done. It mentioned `maxIterations` as a safeguard, with `stopReason: "max_iterations"`.

Objection from the team: **a hard cutoff throws away all the agent's work.** After fifteen iterations of research, returning a truncated result with no written answer is a poor product, especially for a blind person who dictated a request and is waiting for a spoken answer.

Two options proposed: have the agent declare a status (`reasoning` / `tool` / `done`), or have a timer trigger a check asking it whether it is done.

## Why the `status` field is ruled out

**It is `isDone` under another name.** The status would be produced by the model, hence unreliable exactly in the case where it would be useful: an agent that has gone off the rails reports `status: "reasoning"` indefinitely. The symptom is generated by the failing process itself.

And it brings no new information: the tool-call protocol already gives it, for free and reliably:

| Declared status | What already says it |
|---|---|
| `tool` | `toolCalls` non-empty |
| `done` | `toolCalls` empty |
| `reasoning` | does not exist for the loop: it is content |

Net cost: some tokens, a parsing surface, a failure mode. Benefit: none. Same reasoning as the removal of `isDone` (`ADR-AGENT-0003`).

## Options evaluated

**A: Hard cutoff on `maxIterations`.** Simple, predictable, and throws away the work done.

**B: `status` field declared by the model.** Ruled out above.

**C: Budget that triggers a landing.** Instead of cutting off, we ask the agent to conclude with what it has.

## Decision

**Option C**, in two complementary mechanisms.

### 1. Composite budget → landing

The budget is reached as soon as **any one** of the bounds falls: iterations, elapsed time, tokens consumed. Then, rather than returning:

1. Inject a message: "budget reached, conclude with what you have".
2. Call the model again **without passing it any tools**.
3. Return its answer.

**Removing the tools from the last call is what guarantees the landing.** The model *can* no longer call anything: it writes. Without this precaution, it would call a tool again and the loop would restart.

Cost: one extra LLM call. Benefit: a usable answer instead of a truncated result.

### 2. Repetition detector

The reliable signal of being stuck is not what the agent says about its state, it is **repetition**: the same tool, with the same arguments, N times in a row. Observable from the outside, without asking the model anything, and it detects the real pathology: an agent going in circles.

It triggers the same landing, but **earlier** than budget exhaustion.

### `stopReason`

```ts
stopReason: "completed"   // natural end: no tool call
           | "budget"     // bound reached → forced landing
           | "stuck"      // repetition detected → forced landing
           | "error"
```

`maxIterations` remains **as a last net** against a loop bug, not as the main mechanism.

## Consequences

**Positive**

- The user always receives a written answer, never a mutilated result. This is a direct accessibility gain: a person who dictates expects a spoken answer, not silence.
- The repetition detector kicks in before budget exhaustion: we save the wasted iterations.
- **A new, free evaluation metric**: "does this model conclude on its own, or does it always hit the budget?" A model at 100% success but systematically ending in `"budget"` is not the same product as a model that terminates naturally. That is exactly the kind of difference the harness must surface (`ADR-AGENT-0006`).
- Bounding by time and by tokens is model-agnostic: comparing two models on "10 iterations" does not mean the same thing as on "30 seconds" or "50,000 tokens".

**Negative**

- One more LLM call on each forced exit. Negligible next to the iterations already consumed.
- Three bounds to configure instead of one. Mitigated by reasonable defaults: the consumer only sets one if it has a reason to.
- The repetition detector can have false positives: an agent legitimately re-reading the same file twice. The threshold must therefore be ≥ 3, and this is a landing, not an error: the cost of a false positive stays low.

**What does not change**

The natural termination from `ADR-AGENT-0003`: empty `toolCalls` ⇒ `"completed"`. The budget and the detector are **fallback** mechanisms, never the nominal path.
